## 검증 환경과 근거

- 기존 `hankan` DB는 초기화하지 않았다. 별도 폐기용 Supabase 프로젝트 `hankan-stage11-20261028`, API 55321/DB 55322 포트에 001~009 마이그레이션을 처음부터 적용했다.
- 단위/UI는 Vitest·Testing Library(jsdom), 권한·트랜잭션·동시성은 실제 PostgreSQL(pgTAP)과 로컬 Supabase 통합 검사다. jsdom은 렌더링·OS 권한·푸시 수신 검증을 대신하지 않는다.
- 최종 명령 결과와 독립 리뷰 결과는 아래 결과 절에 기록한다. 선택적 AI-live skip은 통과 건수에 포함하지 않는다.
- 8단계 실제 API 평가와 수동 영수증 검증은 [AI 평가 기록](ai-evaluation.md)에 있다. 사용자가 ①날짜 필수/자동 등록 없음 ②품목 수정·제외 후 저장 ③선택 품목 1회 저장·새로고침 보존을 직접 통과했다고 확인했다. 이는 과거 빌드의 사용자 검증이며 이번 단계의 새 CUA 실행이 아니다.
- 5단계의 320/390/768/1280px·200% 확대·키보드·테마 검증도 과거 화면 검증이다. 새 알림 연결/상세 화면까지 통과한 것으로 확대하지 않는다.
- 이번 CUA의 원래 로컬 주소 `http://127.0.0.1:3000/` 접근은 저장된 사용자 권한/관리 정책에서 거부됐다. 다른 브라우저·원시 CDP·HTTP로 화면을 대신 읽지 않았다.
- 2026-10-28 당시 사용자는 HTTPS·지원 기기 환경이 없다고 확인했다. 2026-10-29 사용자가 승인한 Vercel 배포로 HTTPS 주소를 확보했다. 사용자 도메인·DNS 변경은 수행하지 않았다.

## 직접 이어서 확인할 화면 절차

기존 데이터를 쓰지 말고 폐기용 두 계정 A/B와 확인용 재료를 만든다. 같은 아이디를 두 사람이 공유하지 않는다. 각 행의 실제 결과·브라우저/OS·빌드 커밋·검사 시각을 기록한다.

1. A/B 각각 아이디·비밀번호 가입→즉시 로그인. 본인 냉장고만 보이고 서로 다른 재료가 분리되는지 확인한다. 같은 이름 두 묶음을 서로 다른 날짜/남은 양으로 저장한 뒤 새로고침·재로그인한다. 비밀번호 변경의 두 입력 일치를 확인하고, 분실 시 관리자 CLI 초기화 후 이전 비밀번호가 거부되는지 확인한다.
2. A가 초대를 만들고 B는 로그인 후 냉장고/권한을 읽고 직접 참여한다. 수락 전 접근 차단, 수락 후 공동 편집을 확인한다. 취소·사용된·만료된 링크는 접근을 허용하지 않아야 한다.
3. A/B가 같은 재료 편집 창을 열고 A부터 저장한다. B 저장은 충돌 안내와 B의 입력 보존이 필요하다. 한쪽 삭제 후 다른 쪽 저장도 복원하지 않아야 한다.
4. B가 영수증 검토와 추천을 열어 둔 상태에서 A가 B를 내보낸다. 목록 갱신 시 재료가 사라지고 수정/추천/초안 저장·파일 재조회가 차단되는지 확인한다. A의 재료는 유지돼야 한다. B 나가기도 반복한다.
5. 합성 영수증은 사용자가 파일 선택으로 올린다. 분석만으로 재료가 생기지 않고 날짜가 비어 있어야 한다. 날짜 없이 저장 차단→품목 수정/제외→날짜 선택→저장→새로고침을 확인한다. 손상 파일은 오류 후 다시 선택 가능해야 한다.
6. 추천 두 그룹, 전체 필요 재료/부족 재료, 양·순서·시간·인분·생성형 표시를 확인한다. 조회 전후 남은 양은 같아야 한다. 냉장고 전환 중 늦은 응답이 새 목록에 섞이면 실패다.
7. 오프라인 전환→저장 실패/입력 보존→네트워크 복구 후 재시도를 확인한다. 테마를 바꿔도 입력이 남고, 320px·390px·데스크톱·200% 확대에서 겹침/가로 넘침이 없어야 한다. Tab/Shift+Tab/Esc로 Dialog 가두기·닫기·초점 복귀를 확인한다.

## 실제 푸시 절차 — 환경 준비 후 수행

HTTPS에서 웹과 지속 worker, Supabase 인증 redirect를 같은 서비스 주소로 구성한다. [운영 준비](operations.md)를 따른다. OS 알림 권한·집중 모드도 확인하되 접근 정책을 우회하지 않는다.

1. 데스크톱 Chrome 또는 Android 지원 브라우저에서 설치·로그인한다. iOS/iPadOS 16.4 이상은 Safari 공유→홈 화면 추가→설치된 앱에서 별도로 검사한다.
2. 두 계정에 오늘~3일 이내 재료를 넣고 알림 일정을 서로 다른 미래 시각으로 저장한다. 각 기기에서 **브라우저 알림 연결**을 눌러 허용한다. 자동 권한 요청이 나타나면 실패다.
3. 각자의 지정 시각에 본인 알림이 한 번 도착하고 재료 이름 없이 개수만 보이는지 확인한다. 클릭하면 로그인과 현재 권한을 거친 본인 상세로 이동해야 한다.
4. 같은 날 시각을 바꾸고 worker를 재시작한다. 이미 받은 요약이 다시 표시되면 실패다. 아직 보내지 않은 빈 요약을 나중 시각으로 바꾼 경우는 새 재료가 있으면 그 시각에 한 번 받아야 한다.
5. 브라우저 연결 해제 후 그 기기만 중단되는지, 계정 일정 끄기는 모든 서버 구독을 제거하는지, 로그아웃은 현재 브라우저만 제거하는지 확인한다. 다시 켜면 재연결이 필요하다.
6. 알림 생성 후 공유 냉장고에서 나가거나 내보내진 뒤 클릭한다. 현재 접근 가능한 재료만 보이고 제거된 냉장고 내용은 없어야 한다.

## 최종 결과

- 새 DB 적용/전체 자동 검사: 001~009 신규 적용 및 각 명령 exit 0. DB 101건 + 단위/UI 202건 + 실제 DB 통합 94건 = 397건 통과. TypeScript·ESLint·웹 production build·worker bundle 통과. 같은 수정본으로 원래 로컬 환경의 check:stage11도 exit 0이며 빌드 접속 설정을 원래 주소로 복구했다.
- 실제 OpenAI 2건: HANKAN_AI_LIVE=1로 별도 실행해 2/2 통과. 영수증의 비식품/지시문 제외·날짜 미반환과 생성형 조리법의 전체 재료/양/단계/시간/인분·출처를 확인했다. 기본 통합의 선택적 skip 2건은 통과로 집계하지 않는다. 합계 399건은 자동/실제 API 계층을 구분한 수치다.
- 독립 코드 리뷰: Critical 0건, Important 2건, 보류 Minor 0건. 두 결함을 실제 DB 테스트에서 재현 후 수정했다. [리뷰와 결정](release-review.md)에 근거를 기록하며, 추가 마이그레이션 009까지 새 DB에 적용한 뒤 전체 검사를 다시 통과했다. 원래 로컬 DB에도 기존 데이터를 초기화하지 않고 009를 추가 적용했다. 새 DB와 기존 DB의 public 타입 정의도 동일하다.
- 비밀/의존성 검사: npm audit --omit=dev의 알려진 취약점 0건. 브라우저 정적 번들 19개에서 검사한 서버 비밀 값 3종의 노출 0건. 실제 비밀 값은 출력하거나 문서에 저장하지 않았다.
- 실제 CUA 사용자 흐름: 권한 정책 차단으로 미검증. 과거 수동/시안 검증과 혼합하지 않는다.
- 실제 HTTPS 푸시·iOS 설치·모바일 파일 선택: 환경 없음으로 미검증. 공개 릴리스 조건으로 유지한다.

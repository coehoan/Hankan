# 비동기 요리 추천

추천 요청은 재료 목록과 사용자 시간대를 기준으로 한 날짜를 DB에 저장하고 즉시 접수한다. 새 추천은 AI만 실행한다. 과거 식약처 결과는 저장된 내역에서 열 수 있다. 화면을 닫아도 서버 작업과 저장된 결과는 유지된다. 주 메뉴의 **추천 내역**에서 최근 30건을 열 수 있다.

## API와 저장된 화면

- 접수: POST `/api/fridges/:fridgeId/recipes`, UUID `{requestId}`, HTTP 202 `{data: RecipeJob}`. 이전 빈 `{}` 동기 API 계약은 사용하지 않는다.
- 내역: GET `/api/recipe-jobs`, 선택적으로 `fridgeId`, `latest=1`. 기본 최근 30건, latest는 1건이다.
- 전역 상태: GET `/api/recipe-jobs?activity=1`, 최근 30건의 id/status만 반환한다.
- 저장 결과: GET `/api/recipe-jobs/:jobId`, 화면 `/recipes/jobs/:jobId`. 내역 화면은 `/recipes/history`다.
- 내역 삭제: DELETE `/api/recipe-jobs/:jobId`, 성공 시 HTTP 204. 요청자이면서 현재 냉장고 멤버인 사용자가 종료된 내역을 한 건씩 삭제할 수 있다. 삭제 시 목록과 상세 조회에서 숨기고, 결과와 중복 요청 방지 기록은 보존한다.
- 모두 로그인과 현재 RLS 권한을 검사하고 private/no-store로 반환한다. `RecipeJob` 계약은 `src/features/recipes/job-contracts.ts`가 기준이다.

## 실행과 복구

- POST `/api/fridges/[fridgeId]/recipes`는 `{requestId}`를 받아 HTTP 202와 작업을 반환한다. 동일 요청 번호와 이미 진행 중인 작업은 재사용하며, 합쳐진 요청 번호도 별도로 저장한다. 접수 응답이 끊기면 클라이언트는 같은 번호로 복구한다.
- Next `after`가 응답 뒤 즉시 실행한다. 중단된 작업은 기존 매분 worker가 회수한다. 독립 worker도 같은 큐를 사용하며 알림 설정 없이 실행 가능하다. 일일 알림 발송과 추천 처리는 병렬이다.
- 작업은 120초 lease와 매번 바뀌는 token으로 보호하며 최대 세 번 회수한다. AI 호출은 50초로 제한하고 결과를 검증해 저장한다. 복구 시 이미 저장된 AI 결과는 다시 생성하지 않는다. 이전 작업에 대기 중인 식약처 단계가 있으면 외부 호출 없이 종료하며, 이미 저장된 결과는 보존한다.
- 목록과 상세는 추천 당시 재료 기준이다. 현재 재료나 날짜가 달라지면 안내하고, 추천 자체는 재료·남은 양을 변경하지 않는다. 출처 표시는 기존처럼 숨긴다.
- 일반 조리용 물은 냉장고에 등록하지 않아도 보유한 것으로 계산한다. 레시피에는 물의 필요량을 표시하고, 추가 구매 목록에는 넣지 않는다. 다른 재료가 필요한 요리는 물 외에 사용할 수 있는 보유 재료가 하나 이상 겹쳐야 추천에 표시한다.
- AI에는 보유한 핵심 재료를 기준으로 기존 요리를 최대 4개 추천하도록 요청한다. 요리권별 우선순위나 할당량은 두지 않는다. 보유 재료와 물로 만들 수 있는 요리를 먼저 고르고, 추가 구매 후보는 부족한 필수 재료가 최대 두 종류일 때 포함하도록 안내한다. 총 소요 시간과 함께 각 단계에 필요한 도구, 불 세기, 시간과 완료 상태를 적도록 요청한다.
- 진행 중인 작업만 화면에서 조회한다. 추천 결과 2초, 내역 3초, 전역 상태 5초 간격이며 숨겨진 화면이나 오프라인에서는 멈추고 복귀 시 갱신한다.

## 개인정보와 알림

추천 진행 영역은 `요리를 추천하고 있어요`와 `결과는 추천 내역에 저장돼요. 알림을 켜 두면 완료 소식도 받아요.`로 안내한다. 일부 결과가 먼저 준비되면 기존 부분 결과 안내 제목을 유지한다. 회색 진행줄은 표시하지 않으며 진행 중에는 별도 물·재료량 안내도 숨긴다. 알림 설정 API에서 꺼짐을 확인한 경우에만 `알림 설정하기` 링크를 표시하고 `/mypage#notifications`로 이동한다. 설정 조회 중·실패·켜짐에는 링크를 표시하지 않으며 화면 포커스 및 온라인 복귀 시 다시 확인한다.

추천 상태는 앱 화면 위에 떠 있는 팝업으로 표시한다. 화면 최상단에 고정하며 위쪽 여백은 16px과 기기 안전 영역 중 큰 값을 사용한다. 모바일에서는 가운데에, 넓은 화면에서는 오른쪽에 뜨고 스크롤해도 같은 위치를 유지한다. 완료·실패 팝업을 누르면 해당 결과 화면으로 이동하며 팝업이 닫힌다. 결과 화면을 열거나 닫기 버튼으로 팝업을 닫은 뒤에는 같은 작업의 팝업이 다시 뜨지 않는다. 진행 중 팝업에도 닫기 버튼을 표시한다. 작업별로 처음 표시한 뒤 3초 후 자동으로 닫히거나 사용자가 직접 닫을 수 있으며, 같은 작업의 상태 갱신이나 화면 이동으로 다시 표시하지 않는다. 진행 팝업이 닫힌 뒤에도 상태 확인은 계속하며 완료·실패로 바뀌면 팝업을 다시 표시한다. 완료·실패 팝업은 자동으로 닫지 않고 사용자가 결과로 이동하거나 닫을 때까지 유지한다.

요청자이면서 현재 냉장고 멤버인 사용자만 작업과 결과를 조회한다. 클라이언트가 스냅샷·사용자·결과·worker token을 지정하거나 수정할 수 없다. 실행과 결과 저장 때 멤버십을 다시 검사한다. 요청자별 시간당 새 작업은 10건으로 제한한다.

기존 알림 설정이 켜져 있고 유효한 푸시 구독이 있을 때 완료 알림을 보낸다. 전송마다 현재 설정과 멤버십을 다시 확인하고, 성공한 구독은 기록해 재시도에서 제외한다. 서비스 워커는 현재 로그인 사용자와 저장된 추천의 고정 경로만 허용한다. 실제 기기에서의 푸시 수신은 자동 테스트와 별도다.

## 원하는 재료로 추천받기

재료 목록을 불러오지 못한 경우 추천 화면의 ‘재료 다시 불러오기’로 현재 냉장고를 재조회한다. 결과는 요리가 있는 분류만 표시하며, 모든 결과가 비어 있으면 기존 빈 결과 안내를 유지한다.

요리 추천 화면에서 `전체 재료` 또는 `재료 골라서`를 선택한다. 전체 모드가 기본이며, 선택 모드는 고른 재료를 최소 하나 활용하는 요리를 찾는다. 선택하지 않은 보유 양념과 재료도 함께 활용한다. 물만 기본 제공하는 기존 원칙은 유지한다.

사용 가능한 재료(남은 양 > 0, 기한이 오늘 이후)를 이름 정규화 기준으로 묶는다. 같은 종류의 여러 재고는 한 번에 선택되며, 선택 영역에서 이름 검색과 12종씩 더 보기를 지원한다. 검색과 모드 전환은 선택 초안을 유지하고 냉장고 전환은 초기화한다. 공유 재고에서 소진·삭제·기한 변경으로 사용할 수 없어진 재료는 선택에서 제외하고 안내한다.

추천 접수에는 `requestId`와 선택적인 `selectedIngredientIds`를 보낸다. 선택 목록 생략은 전체 추천, 명시적인 빈 배열·중복 ID·다른 냉장고 재료는 오류다. 선택은 최대 1,000개 재고 ID이며 API 본문은 64KiB로 제한한다. 서버는 하나의 재고 스냅샷에서 선택을 검증하고 같은 스냅샷을 저장한다. UI가 전달한 재료명이나 스냅샷은 사용하지 않는다.

같은 requestId 재시도는 원래 조건의 작업으로 돌아간다. 다른 조건으로 같은 requestId를 사용하거나 다른 조건의 작업이 진행 중이면 충돌을 반환한다. 같은 조건의 진행 중 작업만 병합하며, 기존 requestId 복구와 별도로 새 별칭은 최근 1시간 내 생성 작업 기준 사용자당 100개로 제한한다. 새 작업은 기존 시간당 10건 한도를 유지한다.

AI에는 전체 보유 재료와 선택 재료의 이름을 별도로 전달한다. 선택 재료와 전혀 겹치지 않는 결과는 서버에서 제외하며, 부족 재료는 전체 보유 재료로 계산한다. 선택 재료가 요리에서 의미 있게 쓰이는지는 프롬프트 지시이며 문자열 검사로 완전히 보장되지는 않는다. 저장된 내역 목록과 상세에는 요청 당시 선택 조건을 표시하고, 기존 내역은 전체 추천으로 해석한다.

### 적용과 검증 상태 (2026-11-11)

`20261111083903_selected_recipe_ingredients.sql` 적용이 필요하다. 이 변경은 `enqueue_recipe_job(uuid,uuid)`를 선택 목록 기본값이 있는 `enqueue_recipe_job(uuid,uuid,uuid[])`로 교체하므로 기존 2인자 요청도 동작한다. 클라우드 적용과 배포는 아직 하지 않았다.

후속 확인(2026-11-12): 위 문단은 적용 전 기록이다. 운영 마이그레이션 이력에서 `20261111083903`을 확인했으며, `377bccd`의 Actions 성공과 Vercel READY를 확인했다. 이미 적용한 SQL을 재실행하지 않는다. 이후 UX 변경에는 추가 마이그레이션이 없다.

후속 세션에서 기존 loopback DB에 migration을 적용하고 CLI 타입 재생성·비교, pgTAP 125개, 통합 135개, DB 보안 검사를 통과했다. 선택적 실 API 2개는 스킵했다. 단위·컴포넌트 479개(51파일), 타입·전체 포맷·제품 빌드(Node 24.15.0)·worker 빌드·배포 보호 59개도 통과했다. 린트 오류 0, 기존 경고 3개다.

실제 React 컴포넌트와 현재 CSS를 합성 데이터·가짜 API로 브라우저에서 확인했다. 선택 UI는 라이트/다크, 320·390·844·1440px, 검색·선택 복원·선택 POST·진행 잠금·완료 조건·키보드를 검사했다. 팝업은 같은 테마·화면 폭에서 레이아웃 밀림 없음, 스크롤 고정, 완료 전환·키보드 닫기를 확인했다. 실제 로그인·AI·실기기 푸시는 별도 확인이 필요하다. 운영 적용은 승인된 dev push 파이프라인의 Actions·migration 이력·Vercel READY로 확인한다.

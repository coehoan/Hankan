# 개인별 알림 일정 — 9단계

냉장고·요리 추천 화면의 **알림 설정**에서 본인 계정의 알림 일정과 매일 받을 시각을 저장한다. 소유자와 공유 멤버 모두 자기 설정만 사용한다. 냉장고를 바꿔도 다른 사람의 시각을 적용하지 않는다.

기본값은 `enabled=false`, `localTime=09:00`, `timezone=Asia/Seoul`, `nextRunAt=null`이다. 현재 계정의 프로필 시간대를 사용하며 API는 사용자 ID·시간대·다음 실행 시각·마지막 발송일 입력을 받지 않는다. 화면은 브라우저 알림 연결이 별도임을 표시한다. 아직 권한 요청·푸시 구독·실제 발송은 하지 않는다.

## 예약 규칙

- 현재 서버 시각을 사용한다. 오늘 미발송이고 설정 시각이 미래이면 오늘 예약한다.
- 설정 시각이 현재와 같거나 과거이거나, 오늘 이미 발송했으면 다음 현지 날짜로 넘긴다.
- 꺼짐은 `nextRunAt=null`로 반환하며 저장한 시각과 마지막 발송일은 보존한다. 같은 날 다시 켜도 이미 발송했다면 내일부터다.
- UTC로 저장하고 계정 시간대로 표시한다. 자정·연말·윤일·분 단위 오프셋을 처리한다. 서머타임 반복 시각은 나중 시각을 선택하고 존재하지 않는 시각은 전환 간격만큼 앞으로 이동한다. JavaScript와 PostgreSQL에 같은 고정 사례를 적용했다.

| 현재 UTC | 시간대 | 시각 | 마지막 발송일 | 다음 UTC |
| --- | --- | --- | --- | --- |
| 2026-10-26 00:00 | Asia/Seoul | 20:30 | 없음 | 2026-10-26 11:30 |
| 2026-10-26 10:00 | Asia/Seoul | 18:00 | 없음 | 2026-10-27 09:00 |
| 2026-10-26 00:00 | Asia/Seoul | 20:30 | 2026-10-26 | 2026-10-27 11:30 |

서머타임 해석은 [PostgreSQL의 규칙](https://www.postgresql.org/docs/17/datetime-invalid-input.html)을 따른다. JavaScript는 표준 `Intl.DateTimeFormat`의 시간대 정보로 UTC 오프셋을 구해 같은 결과를 낸다. 추가 날짜 패키지는 사용하지 않았다.

## 데이터 및 API

기존 영수증 검토 마이그레이션이 005를 사용하므로 `006_notification_preferences.sql`로 추가했다. 기존 사용자는 프로필 기준으로 기본 설정을 채우고, 새 사용자는 프로필 생성 트리거에서 함께 만든다. 프로필 시간대 변경은 동일 트랜잭션에서 검증·동기화한다. 기존 사용자·재료를 삭제하거나 DB를 reset하지 않는다.

`public.notification_preferences`의 `user_id`는 계정당 유일하다. RLS는 본인 조회만 허용하며 일반 계정의 직접 INSERT/UPDATE/DELETE는 허용하지 않는다. `save_notification_preferences(jsonb)` RPC가 인증된 본인의 설정만 갱신한다. `next_run_at`은 DB 트리거가 계산하고 `last_sent_local_date`는 클라이언트가 바꿀 수 없다.

| 요청 | 본문 | 응답 |
| --- | --- | --- |
| GET `/api/settings/notifications` | 없음 | `{data: {enabled, localTime, timezone, nextRunAt}}` |
| PATCH `/api/settings/notifications` | `{enabled: boolean, localTime: "HH:mm"}` | 같은 형식의 저장 결과 |

로그인이 필요하며 응답은 `private, no-store`이다. 변경 요청은 같은 Origin과 JSON 형식을 검사하고 본문을 제한한다. 알 수 없는 필드, 잘못된 시·분, 유효하지 않은 시간대는 거부한다. 저장 실패·오프라인에서는 저장된 요약을 유지하고, 폼의 수정값은 재시도용으로 남긴다. 초기 조회 실패 시 가짜 기본값으로 저장하지 않는다.

## 다음 단계 연결 계약

10단계는 이 설정 테이블과 마지막 발송일을 그대로 사용한다. `enabled=false`와 `nextRunAt=null`은 구독 제거로 이어질 신호다. 발송 성공 후 마지막 현지 발송일을 기록하고, 예약 계산은 `private.next_notification_at`을 재사용한다. 실제 알림 중복 방지는 10단계의 사용자+현지 날짜별 작업과 발송 기록으로 보완한다. 9단계만으로 푸시를 수신하거나 전체 서비스가 완료된 것으로 표시하지 않는다. 다음 마이그레이션 번호는 007부터 사용한다.

## 검증 범위

고정 시각의 오늘·내일·동일 시각·당일 발송·자정·윤일·서머타임, 기한 오늘/3일/4일 분류, 실제 DB의 개인 접근·소유자/멤버 간 차단·재로그인 복원·on/off·예약 메타데이터 변조 차단을 검사한다. 실제 설정 대화상자와 AppShell을 렌더하여 저장·재시도·오프라인·조회 실패·다음 예정 표시·다른 대화상자와의 전환도 검사한다. 브라우저 권한과 실제 푸시 수신 검증은 후속 PWA 단계의 범위다.

```powershell
npm.cmd run check:stage9
```

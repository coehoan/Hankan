# 선택 재료 중심 요리 추천 설계

작성일: 2026-11-11. 상태: 2026-11-11 사용자 상세 설계·시안 승인, 로컬 구현 및 검증 진행.

## 목적과 합의

기존 전체 재료 추천을 유지하면서 사용자가 원하는 재료를 골라 그 재료를 활용하는 요리를 찾는다. 선택하지 않은 보유 재료와 양념도 함께 활용한다. 여러 재료를 선택하면 각 추천 요리는 선택 재료를 최소 하나 이상 사용한다. 모든 선택 재료를 한 요리에 넣거나 선택 재료마다 결과 하나를 보장하지 않는다.

물만 기본 제공한다. 다른 재료는 실제 보유 목록으로 판단한다. 기존 최대 4개 요청, 현실적인 기존 요리, 추가 구매 필수 재료 최대 2종, 다양한 요리권, 구체적인 분량·조리 단계 원칙을 유지한다. 추천은 재고를 차감하지 않는다.

## 접근 방식

| 검토한 방식 | 장점 | 부담 | 결정 |
| --- | --- | --- | --- |
| 추천 화면 내부에서 선택 | 조건과 실행 버튼을 함께 확인하고 바로 수정 | 재료가 많을 때 목록 길이 관리 필요 | 사용자 선택 |
| 별도 선택 창 | 기본 화면이 짧음 | 수정할 때 창을 다시 열어야 함 | 미채택 |

선택한 재료만 사용하도록 보유 목록을 축소하는 방식은 채택하지 않는다. 전체 보유 목록과 선택 목록을 별도로 전달한다.

## 화면 구성과 문구

기존 요리 추천 페이지 제목 아래, 추천 결과 위에 조건 영역을 둔다. 내역 상세에서는 조건을 읽기 전용으로 표시한다.

| 순서 | 요소 | 동작·문구 |
| --- | --- | --- |
| 1 | 추천 방식 | `전체 재료` / `재료 골라서` 라디오 그룹. 최초 진입 기본값은 전체 재료 |
| 2 | 선택 안내 | 선택 모드에서 `어떤 재료를 먼저 쓰고 싶나요?` / `고른 재료를 중심으로, 냉장고의 다른 재료도 함께 활용해요.` |
| 3 | 재료 찾기 | 이름 검색. 보이지 않는 재료도 검색하고 선택 상태는 유지 |
| 4 | 선택 요약 | `선택한 재료 2종` 및 선택한 이름 목록. `선택 해제`는 전체 선택을 해제 |
| 5 | 재료 선택 목록 | 체크 표시·재료명·가장 가까운 기한을 가진 버튼. 줄바꿈하는 칩 모음 |
| 6 | 목록 펼침 | 최초 12종, `더 보기`마다 12종 추가. 검색 중에도 동일. 선택 요약에는 검색에 숨은 선택도 유지 |
| 7 | 실행 | 전체 모드 `요리 추천 받기`, 선택 모드 `선택한 재료로 추천받기` |
| 8 | 결과 조건 | 저장된 요청 기준으로 `전체 재료로 추천` 또는 `선택 재료: 두부, 계란` 표시 |

선택 모드에서 0종이면 실행을 비활성화하고 `추천에 활용할 재료를 골라 주세요.`를 표시한다. 전체 모드에서 재료가 없을 때는 기존 버튼 비활성화 방식을 유지하며 불필요한 빈 재고 패널을 추가하지 않는다.

## 시각 디자인

- 기존 초록색, Pretendard, `design-system.css`의 surface·soft·accent·border·foreground 토큰을 사용한다. 새로운 색상 체계를 도입하지 않는다.
- 모드 전환은 낮은 높이의 두 칸 선택 컨트롤로 표현한다. 선택 항목에는 배경과 체크 표시를 함께 써서 색상에만 의존하지 않는다.
- 재료 버튼은 최소 44px 높이, 버튼 간격 8px, 영역 내부 간격은 16/24px를 사용한다. 긴 재료명은 줄바꿈하고 가로 스크롤을 만들지 않는다.
- 모바일은 설명 → 검색 → 선택 요약 → 재료 → 실행 순서의 한 열로 배치하고 실행 버튼은 영역 너비를 채운다. 데스크톱은 제목·설명과 실행 버튼을 같은 조건 영역 안에서 정렬한다.
- 결과를 밀어내는 거대한 카드나 중첩 카드 대신 얕은 배경과 구분선으로 조건 영역을 묶는다. 기존 떠 있는 추천 상태 팝업과 메뉴는 유지한다.
- 라이트·다크 모두 의미 토큰을 사용하고 선택 상태·초점·비활성 상태를 별도 확인한다. 폰트 확대와 reduced-motion을 지원한다.
- 네이티브 라디오와 `button aria-pressed` 또는 체크박스를 사용한다. 선택 개수 변경은 문맥이 있는 단일 상태 영역으로 알리고 초점을 이동하지 않는다.

## 재료 단위와 화면 상태 — 구현 제안

아래 항목은 기존 코드를 바탕으로 정한 제안이며 사용자의 별도 확정 사항은 아니다.

- 선택 대상은 기존 `usableIngredients`와 동일하게 남은 양이 0보다 크고 기한이 지나지 않은 재료다. 오늘 기한인 재료는 포함한다.
- 같은 정규화 이름의 여러 재고는 한 종류로 묶고 가장 가까운 기한을 표시한다. 선택한 종류는 접수 시점의 유효한 재고 ID들로 서버가 확인한다. 선택은 보유량이 충분하다는 보장이 아니다.
- 정렬은 임박 재료 우선, 다음 기한순·이름순이다. 기존 정규화 규칙을 재사용하고 임의의 동의어 추론을 추가하지 않는다.
- 전체/선택 모드를 바꾸어도 같은 냉장고에 머무는 동안 선택 초안을 유지한다. 냉장고 전환 시 선택·검색·표시 개수를 초기화한다. 새로고침 후 선택 초안의 영구 보존은 1차 범위에서 제외한다.
- 공유 재고 갱신으로 선택 재료가 없어지거나 사용 불가가 되면 선택에서 제외하고 안내한다. 사용자 요청을 전체 추천으로 자동 전환하지 않는다. 접수 직전 서버에서도 재검증한다.
- 추천 진행 중에는 조건을 잠그고 기존 진행 상태를 표시한다. 완료 후 조건을 바꿔도 기존 결과의 조건 표시는 저장된 요청을 따른다.
- 실패 후 재시도는 같은 조건을 유지한다. 응답 유실 후 복구 요청은 원래 requestId와 조건을 함께 유지한다. 조건을 바꾸어 새로 요청할 때는 새로운 requestId를 사용한다.

## 서버·저장·추천 계약

현재 API는 requestId만 받으며 DB RPC가 재고 스냅샷을 생성한다. 따라서 UI에서 전체 재고를 잘라 보내는 방식으로 구현하지 않는다.

- 요청에 선택 재료 ID 목록을 선택적으로 추가한다. 생략하면 기존 전체 추천이다. 명시적인 빈 배열은 잘못된 선택 요청으로 처리한다.
- 입력 UUID·중복·크기를 검증하고, DB 트랜잭션 안에서 냉장고 멤버십과 각 선택 ID의 소속·사용 가능 여부를 확인한다. 임의 이름이나 클라이언트 스냅샷은 신뢰하지 않는다.
- 전체 보유 스냅샷과 선택 ID 목록을 작업에 함께 보존한다. 과거 행은 선택 조건 없음으로 해석한다. 내역 삭제·권한·푸시 동작은 유지한다.
- 현재 사용자·냉장고 단위 실행 중 작업 병합은 선택 조건까지 같을 때만 재사용해야 한다. 다른 조건의 진행 중 작업이 있으면 기존 작업 진행 중임을 알려 조건이 다른 결과를 이번 요청의 결과로 보여주지 않는다.
- 같은 requestId 재전송은 원래 작업으로 복구한다. 같은 ID로 조건을 바꾸면 충돌을 반환한다. 별칭·쿼터·잠금 로직은 마이그레이션 설계 시 함께 검토한다.
- AI에는 전체 보유 재료와 별도의 우선 활용 재료 목록을 전달하고, 각 후보가 선택 재료를 하나 이상 실제 재료 목록에 포함하도록 요구한다. 선택 재료는 핵심 또는 의미 있는 구성 재료로 활용하며 장식적 언급으로 조건을 충족시키지 않는다.
- 서버는 기존 정규화 규칙으로 선택 재료와 전혀 겹치지 않는 결과를 제외한다. 핵심성 판단은 프롬프트 지시이며 문자열 검사로 완전히 보장한다고 주장하지 않는다.
- 부족 재료는 전체 스냅샷과 비교한다. 선택하지 않은 보유 재료를 추가 구매로 표시하지 않는다. 저장 결과를 읽을 때도 저장된 선택 조건을 적용한다.
- 선택 조건에 맞는 결과가 없으면 `고른 재료로 추천할 요리를 찾지 못했어요`와 조건 변경 안내를 보여준다. 전체 추천으로 조용히 대체하지 않는다.

## 영향 범위와 검증

예상 수정 범위: RecipeResults와 재료 선택 컴포넌트·스타일, useRecipeJob의 제출·복구 상태, 추천 접수 API·jobs·DB RPC와 타입, AI 입력 계약·프롬프트·worker, 결과 분류·내역 조건 표시, 관련 문서·테스트.

필수 검증: 기존 전체 추천의 호환성, 선택 재료 포함 필터, 보조 재료 보유 판정, 중복 이름, 0종 선택, 다른 냉장고 ID 거부, 소진·삭제 경쟁, 다른 조건 작업의 병합 방지, 응답 유실 재전송, 과거 내역, 권한 상실, 목록 검색·더 보기·키보드 조작. DB 검증은 `.env.test.local` loopback 환경만 사용한다. 실제 AI 품질과 모의 응답 테스트 결과는 구분한다.

화면 확인: 320/390px 모바일, 가로 화면, 데스크톱, 라이트·다크, 긴 이름·확대 글꼴, 선택 없는 상태·진행·실패·빈 결과. 디자인 문서 작성만으로 브라우저 검증을 완료했다고 보고하지 않는다.

## 범위와 보존

기능 정의와 화면 설계가 이번 단계다. 상세 설계 확인 후 구현 계획으로 넘어간다. 실제 제품 코드 작성, DB 마이그레이션 적용, 유료 AI 호출, 커밋·push·배포는 이 문서 작성에 포함하지 않는다. 현재 미커밋 추천 문구·팝업 수정과 next-env.d.ts를 보존한다.

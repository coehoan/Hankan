# Git Commit

이 스킬은 Git Commit 워크플로우를 정의합니다.
커밋 메시지는 가장 보편적으로 사용되는 **Conventional Commits** 형식을 권장합니다.

## 호출 시맨틱

다음 중 하나라도 해당되면 이 워크플로우를 진행합니다:

- 사용자가 커밋, 체크포인트, 현재 작업을 git에 저장/지속하라고 명시적으로 요청한 경우
- 사용자가 현재 작업을 여러 git 커밋으로 분할해달라고 요청한 경우
- 사용자가 도메인/영역/패키지/기능/파일 그룹/관심사별로 커밋해달라고 요청한 경우
- 사용자가 이 스킬을 직접 호출하거나 참조한 경우
- 주변 하네스가 이 스킬을 git 커밋/체크포인트 작업용으로 명시적으로 선택한 경우

스킬 호출 이후 추가 메시지가 없더라도 호출 자체를 사용자의 명시적 동의로 간주하여 Commmit 을 진행할 수 있습니다.
다만 작업 트리에 관련 없거나, 위험하거나, 모호한 변경이 포함되어 있다면 진행하기 전에 확인을 받는 편이 안전합니다.

## Commit Convention (권장)

컨벤션은 다음과 같습니다. 사용자가 다른 방식을 명시적으로 원하지 않는 한 아래를 따릅니다.

- **권장 규약**: `conventional-commits` (`type(scope): subject` 형식)
  - 다수 프로젝트의 커밋이 이 형식을 따르고 있어, 가독성과 자동화(릴리즈 노트, changelog)에 유리합니다.
  - 사용자가 다른 형식을 원하면 가능한 한 존중하되, 가능하면 동일 PR/작업 안에서는 한 가지 형식으로 통일합니다.
- **언어**:
  - 별도의 사용자 명시적 요청이 없는한 한국어 중심으로 작성합니다. 사용자나 코드 리뷰어가 명시한 언어가 있다면 해당 언어를 사용하여 작성합니다.
  - 영어가 더 자연스러운 경우(라이브러리명, 에러 코드, 외부 API명 등 인용이 많거나 국제 협업 맥락)에는 영어를 섞거나 영어로 작성해도 무방합니다.
- **subject 규칙**:
  - 명령형 현재 시제 (예: `Add ...`, `추가 ...`, `Fix ...`, `수정 ...`)
  - 50자 이내 권장, 최대 72자
  - 마침표(`.`)로 끝내지 않음
- **type** (영문, 소문자) — Conventional Commits의 일반적 값을 참고용으로 안내:
  - `feat`: 새로운 기능
  - `fix`: 버그 수정
  - `docs`: 문서/주석/스킬 안내문
  - `refactor`: 리팩터링 (기능 변화 없음)
  - `test`: 테스트 추가/수정
  - `chore`: 빌드, 패키지, 보조 작업
  - `build`: 빌드 시스템/외부 의존성
  - `ci`: CI 설정/스크립트
  - `perf`: 성능 개선
  - `style`: 포맷팅 등 스타일 변경 (동작 변화 없음)
- **scope** (영문, 소문자, 선택 사항):
  - 영향을 받는 앱/패키지/영역명을 적습니다. 예: `feat(api): ...`, `fix(db): ...`, `docs(agents): ...`
  - monorepo 의 경우 scope 영역을 프로젝트 도메인 중심으로 처리합니다
- **BREAKING CHANGE**:
  - 호환성이 깨지는 변경은 `!` 접미사(`feat(api)!: ...`) 또는 푸터의 `BREAKING CHANGE: 설명` 항목으로 표시하면 좋습니다. 필수는 아닙니다.
- **그외**:
  - `파일 수정`이나 `기타 변경` 같이 모호한 subject는 피합니다.
  - subject 끝에 마침표를 붙이지 않습니다.

## 커밋 메시지 작성 예시

- `feat(lsuite-lite): 코스 상세 조회 API 추가`
- `fix(hasura): 수강신청 transaction 권한 누락 수정`
- `docs(agents): git-commit 스킬 한국어 컨벤션 적용`
- `refactor(admin-common): 공통 페이지 헤더 Component 분리`
- `chore(deps): pnpm 의존성 업데이트`
- `feat(api)!: 응답 envelope 스키마 변경` + 푸터 `BREAKING CHANGE: ...`

## 도메인 분할 원칙

도메인은 단순한 파일 확장자가 아니라 일관된 변경 사유입니다. 각 커밋이 독립적으로 이해 가능하고 리뷰 가능하도록 분할하는 것을 권장합니다.

일반적인 도메인 경계:

- 기능/동작 변경
- 버그 수정
- 리팩터링 또는 코드 이동
- 특정 기능/수정에 대한 테스트와 픽스처
- 문서, 프롬프트, 스킬 안내문
- 설정, 의존성, 빌드 시스템 변경
- 생성된 아티팩트(반드시 커밋해야 하는 경우, 이를 생성한 소스 변경과 묶음)

관련 없는 도메인을 하나의 커밋에 섞지 않는 것이 좋습니다. 다만 사용자가 한 커밋으로 묶어달라고 하면 존중합니다. 강하게 결합된 소스와 테스트 변경은 사용자가 분리 스타일(`테스트만 따로`)을 요청하지 않는 한 함께 두는 편이 자연스럽습니다.

## 워크플로우

1. 저장소 상태 점검:

   ```bash
   git status --short
   git diff --stat
   git diff --cached --stat
   ```

2. 커밋 계획을 세우기 전에 실제 변경 내용을 확인합니다:

   ```bash
   git diff
   git diff --cached
   ```

3. 도메인을 식별하고 커밋 계획을 작성합니다. 각 계획된 커밋에 대해 다음을 포함합니다:

   - 도메인명/목적
   - 포함할 파일 또는 헝크
   - 권장 컨벤션을 따른 subject 초안

4. 관련 없거나, 위험하거나, 생성된 산출물이거나, 비밀값처럼 보이거나, 모호한 변경이 있다면 스테이징하기 전에 사용자에게 포함 여부를 확인합니다.

5. 각 도메인에 대해 해당 도메인만 스테이징합니다:

   ```bash
   git add <paths>
   git add -p <paths>
   ```

   파일 단위 도메인은 pathspec을, 여러 도메인이 섞인 파일은 패치 스테이징을 사용합니다. 현재 커밋 대상 단일 도메인에 가시적인 모든 변경이 속한 경우에만 `git add -A`를 사용합니다.

6. 각 커밋 전에 스테이징된 내용을 검증합니다:

   ```bash
   git diff --cached --stat
   git diff --cached
   git status --short
   ```

   잘못된 도메인이 섞여 있다면 정확히 unstaging 후 다시 스테이징합니다:

   ```bash
   git restore --staged <paths>
   ```

7. 권장 컨벤션(Conventional Commits, 가능한 한국어 subject)으로 스테이징된 도메인을 커밋합니다:

   ```bash
   git commit -m "type(scope): 한국어 또는 영어 subject"
   ```

8. 남은 도메인에 대해 스테이징, 검증, 커밋을 반복합니다.

9. 모든 커밋이 끝난 후 다음을 보고합니다:

   - 각 커밋 해시와 subject
   - 남아 있는 미커밋 변경과 제외 사유

## 안전 규칙

- 스킬 호출 이후 추가 메시지가 없더라도 호출 자체를 사용자의 명시적 동의로 간주하여 Commmit 을 진행할 수 있습니다.
- 다만 아래의 경우에는 진행을 멈추고 사용자에게 확인을 받습니다:
  - 요청한 도메인과 맞지 않는 관련 없거나 위험하거나 모호한 변경이 포함된 경우
  - 비밀값, 로컬 런타임 상태, 의존성 디렉터리, 생성된 캐시처럼 보이는 파일이 섞여 있는 경우
  - 한 커밋에 묶기엔 변경 양이 매우 크거나, 멀티 패키지/monorepo 의 영향 범위가 불명확한 경우
  - 그 외 사용자 의도가 모호해서 잘못 커밋할 위험이 있는 경우
- 명시적 요청이 없는 한 amend, rebase, reset, force-push는 사용하지 않습니다.
- 비밀값, 로컬 런타임 상태, 의존성 디렉터리, 생성된 캐시는 커밋에 포함하지 않습니다.
- 남은 변경을 숨기지 말고 항상 보고합니다.
